# Raspberry Pi Windows 제어: 분석과 설계

조사일: 2026-11-13. 로컬 및 `dy@192.168.0.215:~/windows_control`의 조사 기준 커밋은 `b9add8f`이다.

최신 설계는 [2026-11-18 에이전트 설계](2026-11-18-agent-design.md)를 따른다. 이 문서의 코드 분석·자원은 초기 조사 당시 기록이다. 이후 구현 및 실제 검증 결과는 진행 기록을 참조한다.

## 2026-11-18 설계 업데이트
- 공통 실행기와 목표별 의미 검증을 분리한다. 같은 완료/오류 단어를 모든 task에 적용하지 않는다.
- 목표 조건은 공통 연산의 선언적 조합으로 표현하며 대상 앱/영역/객체·행동 후 근거와 연결한다. task별 전용 코드는 필요한 어댑터에 한정한다.
- decision 모델은 다음 행동·추가 관측·계획 수정·완료 검증을 제안한다. 적재만으로 범용 계획/관측/검증이 완성된다고 가정하지 않는다.
- what to do differently는 관측·차이·행동 이력을 다음 결정에 전달하는 공통 세션으로 구현한다. 구체적인 대안 지식은 목표·정책·모델이 공급한다.
- 현재 단일 행동/TSV 재생 기반 위에 목표 계약 → 세션 → 규칙/모델 비교 → 미지 task 평가 순서로 확장한다. 실제 입력 결과가 불명확하면 재실행하지 않는다.
- 개발용 웹 서버는 현재 작업 PC에서 제공하고 제어 PC 브라우저가 접속한다. Pi는 캡처·OCR·HID를 맡는다.

## 결론
Pi는 화면 수집·OCR·HID 실행을 맡고, 상태 머신 및 재사용 스킬로 일상 작업을 처리하는 구성이 적합하다. 자유로운 요청은 목표 해석·계획기를 추가하고 각 단계의 사후조건으로 검증해야 한다. 모델이 행동을 선택한 것과 실제 작업 성공은 별개다.

## 확인한 자원
| 항목 | 조사 결과 |
|---|---|
| 장비 | Raspberry Pi 4 Model B Rev 1.5 |
| CPU | Cortex-A72 4코어, 최대 1.8GHz, aarch64 |
| 메모리 | 3.7GiB, 조사 당시 가용 약 2.1GiB |
| Swap | 2GiB, 사용 0 |
| 저장 공간 | 루트 58GB, 여유 약 45GB |
| 온도 | 유휴 35.5℃, throttled=0x0 |
| 캡처 | /dev/video0, MJPEG 1920×1080, 설정상 60fps |
| OCR | Tesseract 5.5.0, eng/kor/osd |
| HID | 키보드 8바이트, 마우스 5바이트 |

설정상 프레임 속도는 실제 캡처/OCR 속도가 아니다. OCR·추론 동시 부하와 지속 온도는 추가 측정해야 한다.

## 기존 코드 분석
- `main.rs`: 상시 실행이나 요청 수신 없이 고정된 잠금 해제 경로를 실행한다.
- `agent.rs`: HID와 캡처를 묶고 화면 변화량을 기다린다. 의미적 성공 검증은 없다.
- `task.rs`: 고정 좌표와 순차 입력. OCR 호출의 세미콜론 누락으로 cargo check 실패. Vec를 슬라이스로 차용해야 한다.
- `capture.rs`: stream-to 출력 대상 미지정, JPEG 대신 stderr 반환. 캡처 데이터 경로부터 복구해야 한다.
- `ocr.rs`: TSV 파싱과 프로세스 상태 검사가 없다. 텍스트 박스와 confidence를 활용하지 않는다.
- `hid.rs`: 지원하지 않는 문자 무시, 입력 문자 로그 출력, 종료 마우스 보고서 6바이트 전송 문제.
- `helper.rs`: 별표의 modifier/keycode 순서가 반대다.
- PIN 및 로그인 정보 하드코딩을 제거하고 런타임 입력으로 전환해야 한다.

## 가능한 접근
1. 화면별 상태 머신: 빠르고 검증하기 쉽지만 화면별 개발이 필요하다.
2. 매 단계 모델 판단: 유연하지만 지연·실패·오동작 관리 부담이 크다.
3. 권장 혼합 구조: 검증된 스킬과 상태 머신으로 실행하고 새로운 목표에만 계획기를 호출한다.

## Laya 활용
[Laya 공식 저장소](https://github.com/NandhaKishorM/laya)는 상태·질문·후보에 대한 choice/score/yes-no 결정을 제공한다. 기존 인코더와 Vega 경로가 있으므로 버전·체크포인트·실행 경로를 고정해 평가한다. README의 33ms는 T4 GPU 기준이며 Pi 성능으로 해석하면 안 된다.

환경 정의 + 현재 상태에 다음을 추가한다: 사용자 목표, 현재 단계, OCR 근거, 실행 가능한 행동 후보, 각 행동의 전제·사후조건, wait/reobserve/unsupported 선택지. 선택된 대상의 좌표는 현재 프레임에서 해석한다. 자유로운 요청의 단계 분해·인자 추출·후보 생성은 별도 계획기 책임이다.

우선 별도 PC에서 판단 품질을 확인하고 Pi에는 모델 하나만 적재해 RSS와 p50/p95를 측정한다. 현재 가용 RAM으로 실행 가능성과 실용 지연을 확정할 수 없다. ONNX 경로도 ARM64 및 모델 호환성 확인이 필요하다. [설치 의존성](https://github.com/NandhaKishorM/laya/blob/main/pyproject.toml)

## 권장 구조
사용자 요청 → 목표/조건 해석 → 작업 계획 → 우선순위 큐 → 실행 관리자.
실행 관리자: 캡처 → OCR/화면 분석 → 현재 상태 → 후보 생성/선택 → HID → 새 프레임 사후조건 검증.

- 관측에는 frame_id, 시각, 해상도, 텍스트 박스, confidence를 둔다. 관측과 추론을 분리하고 unknown을 허용한다.
- 화면 변화는 대기 보조 신호다. 성공은 결과 목록·완료 문구·오류 부재 등 작업별 조건으로 확인한다.
- 한 번 행동 후 재관측한다. timeout·OCR 실패·동일 화면 반복을 구분한다.
- HID 소유자는 하나로 제한한다. 긴급 이벤트 선점은 안전한 단계 경계에서 하고 재개 시 다시 관측한다.
- 계획기는 허용된 스킬을 조합하고 실행기가 인자·좌표·프레임·실행 한도를 검증한다.
- 화면 텍스트는 관측 데이터이며 시스템 지시로 취급하지 않는다.

## 테스트 환경
Windows에서 웹 테스트 앱을 띄우고 실제 HDMI/HID 경로를 사용한다. 경보 목록, 검색/필터, 모달, 중복 버튼, 스크롤, 로딩 지연, 실패/재시도를 포함한다. 고정 seed와 초기화로 재현하고 창 크기·배율·테마를 변경한다.

채점기만 정답 상태에 접근한다. 에이전트가 DOM이나 정답 상태로 우회하지 않게 한다. [BrowserGym/MiniWoB++](https://github.com/ServiceNow/BrowserGym)도 후속 평가 후보이며 최종 평가에서는 실제 화면/HID 경로가 필요하다.

평가 계층: 저장 화면/TSV 재생 → 가상 입력 실행 → 실제 HDMI/HID. 성공률, 오클릭, 거짓 성공, 복구율, 긴급 이벤트 지연, 단계별 p50/p95, 최대 RSS를 각각 기록한다.

## 범용화와 진행 순서
같은 앱의 다양한 요청은 스킬 조합으로 시작한다. 여러 앱은 화면/성공 조건 어댑터로 확장한다. 임의 앱의 아이콘·캔버스·숨은 상태는 OCR만으로 한계가 있으며 시각 모델과 별도 평가가 필요하다.

순서: 캡처·빌드·HID 복구 → 폐루프 테스트 환경 → 요청과 스킬 연결 → Laya 정확도/자원 측정 → 미지 화면의 계획기·시각 모델 확장.
